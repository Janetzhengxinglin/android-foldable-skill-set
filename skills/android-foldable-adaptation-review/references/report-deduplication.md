# 同页问题证据去重

采集状态、业务页面和报告证据是三个层次。后台保留完整状态与位置；报告按独立问题发生位置展示，不按截图 ID 计数。

同一业务页面、同一屏幕上下文、同一组件上的同一异常，仅滚动高度、再次进入或采样时间变化时，示例和问题页面汇总各保留一张最清晰的完整代表图。不同页面、方向、窗口、异常组件或新增遮挡／截断不能合并。若同页另一状态揭示新问题或代表图看不见另一发生位置，保留必要的另一张。不能只凭页面名、hash 或相似度自动合并。

在 review-input.json 中可给状态补 logical_page_id；它表示同一业务页面，不等于这些状态可以免审。每条 finding 的 presentation_groups 明确给出：

```json
{
  "id": "same-component-scroll",
  "representative_page_id": "state-a",
  "covered_page_ids": ["state-a", "state-b"],
  "reason": "同页同一组件同一异常，只有滚动高度变化；代表图完整显示异常。"
}
```

每组成员必须同 logical_page_id、同 context_id；代表图必须属于该组且有该问题的实际位置。组需覆盖该 finding 的全部问题状态，且每状态恰好属于一组。缺逻辑页面身份时只允许单状态组。分组由审查者核对原图后填写，脚本不判断图片。

build_report.py 保留 problem_evidence 中全部原始位置和分组映射，展示代表图及其位置。验收分别核对“全部后台证据已归组”和“独立问题位置已在代表图显示”，不要求每张滚动截图重复发布。统计分别使用受审状态数、独立问题类型数、展示页面数，不能把滚动状态数称为受影响业务页面数。

## 问题类型与发生位置

同一可见异常、同一适用要求归为同类问题，换了图案、素材或业务页面不新增问题类型；同一姿态画板内沿用同类编号，各姿态画板仍按用户要求独立从 1 编号；保留全部发生位置，必要时使用多张代表图。问题类型合并与截图去重分别判断：同类问题可以发生在不同页面，不能因此丢掉证据。不同异常或判定条件需分别说明；已确认、观察与待核实状态不得互相替代，同类待核实位置不计为新增已确认问题。

## 跨姿态描述统一

同一问题类型在当前对话各姿态中沿用同一通用标题和核心异常描述，具体页面、图案、边线及组件名称放在位置和证据记录中。既有描述过于具体时统一修订相关描述并保留有效结论，不把新页面的同类异常另造类型。各姿态可使用不同编号，类型身份不由编号决定。

依据性质、结论状态及待明确的证据缺口分别保留，不能为了措辞一致合并不同异常、不同适用要求或把待明确改成已确认；适用条件确有差异时就近说明。同类归并不跨姿态去掉截图，各姿态仍有自己的示例与全部发生位置。发布前核对类型描述一致、结论差异已有依据、当前报告范围内全部有效问题均已映射，不只展示新姿态中新发现的问题。

## 显式保留的问题与待核实项

reported_issues 与 pending_observations 也支持 locations 和 presentation_groups，遵守同一来源完整性与分组规则；兼容旧的单 page_id + bbox_px 格式。每个位置必须在本次受审范围且 bbox_px 位于原图内。多状态组每个位置还须填写稳定 component_key（如 body-right-space），代表图必须覆盖组内全部组件标识；新组件或代表图看不见的新位置需拆组或补代表图。不同滚动坐标但同组件的同一异常可使用同一标识。该标识由原图复审确认，脚本不能代替视觉判断。

这两类项目的全量位置与分组均写入 problem_evidence；汇总只展示必要代表图。待核实项必须显式收录并写出现象和判断依据缺口，普通 not_verified 检查不自动升为问题。范围外来源、未完整分组或代表图遗漏组件均阻止生成报告。


## 逻辑身份先于状态名称

采集名称带“顶部／滚动／加载／再次进入”只是状态，不能直接成为不同业务页身份。同一录屏连续路径与共同导航、标题、组件关系可确认时，在 review-input 工作副本统一 logical_page_id，并保留原名称／来源；中英文别名也要核实后统一。不要把时间戳或截图 ID 放进分组条件来强制拆开重复。

独立条件只保留会改变当前问题判定或导致代表图看不见另一问题位置的差异。例如同一固定控件的重复位置可以用完整加载态代表，纯滚动、内容加载进度或再次进入本身不必拆组；不同弹层／窗口、不同异常对象或新遮挡仍单独保留。跨问题类型可共用一张代表图时同时标出所有编号；同页两张图各展示不同必要问题位置时才都保留。
